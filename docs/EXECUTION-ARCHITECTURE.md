# Execution architecture — P0 candidate

Origin: the real dashboard audit found a complete Node environment and 103 passing VMI assertions, but no production engine calls, incomplete references and unsubstantiated candidate comparisons. Treat this as a control-plane gap, not proof of weak engine creativity.

## P0: executable entry and receipts
Run from the full checkout or portable package using Node 22+. No new third-party dependencies. Use a fresh run directory whose parent exists.

```sh
node scripts/infograph.mjs preflight
node scripts/infograph.mjs start redesign dashboard.html ./run-001
node scripts/infograph.mjs run ./run-001 vmi-explore perspectives.json
node scripts/infograph.mjs run ./run-001 vmi-packet packet.json
node scripts/infograph.mjs verify-vmi ./run-001
```

For create/critique use an actual brief/source file rather than a dashboard. Author perspectives from real evidence using VMI GUIDE and open-discovery; input is an object with a perspectives array. Inspect exploration output before authoring concepts/reviews/scene/styles using the GUIDE and creative/scene references. Packet uses the same perspectives and the existing pipeline contract. The fixture in VMI benchmark/studio-packet.json is for testing only; never use its answers as production input. The CLI loads the canonical ontologies and calls existing engines, never generates concepts or reviews autonomously.

The run records actual source bytes hash, package/version/revision (where available), Node and engine hashes; each stage writes its input, output and execution receipt, or a blocked receipt on an execution error. A packet cannot execute without a replay-verified discovery stage with matching perspectives. Verification replays both stages and compares stored bytes; a result with no preview is still an execution, not design acceptance. No release authorization. Open discovery warnings require independent review. A failed/incomplete run is not a completed design; use a new run directory to retry (P0 limitation). Do not publish run directories with confidential source paths or authored data.

When shell execution is available, start substantive tasks through the CLI and run these VMI stages when the opportunity review justifies a metaphor. When the preflight is blocked or unavailable, disclose actual evidence (including unavailable shell); do not claim execution. Manual mode remains a documented fallback only, not equivalent evidence. Not-applicable metaphors do not need a VMI run; explain why in the opportunity review. P0 does not mechanically enforce task routing or delivery, and cannot stop a host from independently writing files. Local receipts are replayable integrity checks, not signed or tamper-proof attestations. Browser QA and final output/scene binding are separate.

## Roadmap
- P1: revision-bound state machine, integrate existing reconstruction prepare/plan/review and opportunity/quality-depth engines; explicit applicability and next actions.
- P2: progressive authoring templates and lower-friction adapters, discovery/critique iterations, preserve open-ended creativity.
- P3: artifact and screenshot hashes, independent review and integration checks; bind receipts to actual output, not just inputs.
- P4: host-level delivery integration, controlled fallback and adversarial bypass tests. Host-specific enforcement must be demonstrated, not assumed.

## P1a: production pre-build state machine
Use `start-workflow` instead of P0 `start` for substantial work. `status <run-dir>` computes next stage from replay-verified outputs; it is not a release gate. Redesign: reconstruction-prepare ({ir,runtime}), reconstruction-plan (existing authored reconstruction contract), production-plan. Create: production-plan. Critique: reconstruction-prepare, reconstruction-plan with critique scope; no build. production-plan receives {revision,purpose,opportunities,quality,execution}, with existing visual-opportunity, quality-depth and execution-gates input contracts, matching revision/purpose and substantial=true. Author actual evidence, never copy fixture answers. If one slice selects a mechanism, VMI stages are required and both authored inputs must include sliceId. No selected mechanism allows plain design. More than one selected slice, unresolved open-discovery warnings, failed structural audits, or incomplete stages block pre-build eligibility; retries require a new run. P1a does not yet integrate specialized quality-depth engines, final artifact reviews, source extraction, multi-scene VMI, or host delivery enforcement. Source IR hash is checked against actual bytes, but authored observations are not independently verified. Existing P0 commands remain diagnostic-only.

## P1b: specialist compilation
The production plan derives applicable QD01–05 areas and full-workspace applicability from the existing quality-depth context. If applicable, status requires `specialist-plan` before pre-build eligibility. Author {revision,routes} using canonical specialist specifications: QD01 {story,scene}, QD02 choreography spec, QD03 concept spec, QD04 motion spec (uses compiled concept/choreography), QD05 {atlas,spec}. Each route is {mode:"compile",spec}; static QD01/QD02 is allowed only without corresponding runtime need, with reason/evidenceRef, and is explicitly NOT an engine execution. Required QD03–05 cannot be marked static. If all full-workspace flags apply, instead supply {revision,workspace} using the canonical workspace-integration contract; that compiler actually invokes all five compilers and checks shared identities/evidence/route bindings. Spatial atlas IDs must match the production inventory. If a metaphor was selected, include vmiOutputSha256 matching the prior replay-verified packet; this binds records, not semantic equivalence. The current unresolved open-discovery gate still blocks final pre-build eligibility. Outputs preserve per-engine execution dispositions and actual compiler outputs. All outputs are renderer-neutral authored plans; rich assets, narrative truth, real animation, visual review and final artifact binding remain separate. Examples are synthetic test inputs, not production answers. P1b still requires new runs for retry; P2 addresses incremental input and iteration.

## P2a: incremental authoring and immutable retry
Use `node scripts/infograph.mjs task <run-dir> <stage>` to obtain the current stage's assignment, specific reference paths, blank scaffold, locked upstream values and verified output references. Null/empty/not-run fields are intentional; no synthetic answers or pass defaults. Production run inputs may omit upstream-owned fields: reconstruction inputFingerprint, VMI sliceId and packet perspectives, specialist revision and VMI hash. They are deterministically hydrated from replay-verified inputs on execution and replay; conflicting supplied fields block. Raw authored bytes remain stored. P0 diagnostic VMI commands retain explicit inputs.

Use `node scripts/infograph.mjs retry <old-run> <stage> <new-run>` to fork an immutable revision branch at an existing stage. The CLI replays its transitive dependency closure, copies only verified upstream stage files, records lineage and lists invalidated stages. Original evidence remains intact. Then run task/run/status on the new directory; do not reuse downstream receipts. Source or engine changes still require a clean start. This conservative fork model avoids in-place partial rewrites; there is no concurrent-run coordination. P2a provides scaffolds, not an autonomous model or complete JSON schema editor. Multi-scene VMI and open-world candidate expansion remain separate P2b work.

## P2b: bounded multi-scene VMI and local open discovery
Production VMI stages now accept up to eight selected slices. Use {scenes:[{sliceId,perspectives,sourceAdditions?},...]} at exploration and {scenes:[{sliceId,targetId,concepts,reviews,selectedConceptId,scene,styles},...]} at packet; single-scene form remains supported. Each slice is evaluated independently by canonical VMI engines, with exact selected-slice coverage and separate corpus, concepts, previews and issues. A batch only has previewAvailable when every slice has a preview; no merged HTML is implied. Packet perspectives and local additions are hydrated from verified discovery; conflicting edits block. Each optional sourceAdditions record is {query,evidenceRef,verificationNotes,graph}, where graph follows the canonical objects ontology schema with unique ID, source URL, claim, review and limits. Author credible source verification outside the engine; never disclose private target data in search. Additions are isolated to the scene and run, never written to the shared ontology. The adapter checks structure/provenance fields, not truth. Retry vmi-explore to add sources and rerun downstream; the existing open-discovery gate remains conservative (any unresolved perspective blocks build). If no suitable metaphor, fork at production-plan and select a justified plain alternative, preserving the original run; no silent fallback or fabricated approval. Multi-scene compilation is not multi-scene rendering or semantic integration. P2b does not automatically browse the web, guarantee originality or certify final visual quality.

## P3a: artifact binding and observed browser evidence
After replay-verified pre-build eligibility, author actual standalone HTML and a browser plan. Run `node scripts/infograph.mjs bind-artifact <run-dir> <output.html> <browser-plan.json>`, then `node scripts/infograph.mjs browser-review --trusted <run-dir>` and `node scripts/infograph.mjs artifact-status <run-dir>`. Only execute trusted HTML; offline Chromium is not a security sandbox. Browser dependency is the existing optional Playwright/Chromium route (CI pins Playwright 1.51.1 in master engine). Install only with authorization; no automatic installation. Node-only pre-build still works. Plan is {version:1,viewports:[{id,width,height},...],cases:[{id,sliceId,kind:"baseline"|"interaction",steps:[{action:"click"|"select"|"fill",selector,value?}],checks:[{selector,textIncludes?}]}]}. Minimum one baseline case for each declared slice, desktop and mobile, max 100 captures. Interaction cases need a text outcome check. Review actual coverage; declared inventory may itself be incomplete. Browser checks visible essential element bounds, hidden/clipped ancestors, document overflow-x, SVG viewBox overflow (conservative; decorative or intentionally cropped geometry may need redesign or later explicit review), page errors, blocked external resources and authored text outcomes; saves full-page screenshots and hashes per case. No arbitrary JS probes. Artifact and plan snapshots and design-stage hashes bind evidence; altered output or captures block verification. Browser evidence verification checks bytes and coverage, not fresh browser replay or signed provenance. Missing browser is blocked, never treated as pass. P3a does not certify aesthetics, animation continuity, overlap/contrast, data parity or delivery. P3b will integrate actual critique and output revision repair. Browser QA runs once per bound artifact; fresh run required for new captures in P3a.

## P3b: screenshot-bound critique and artifact repair
After browser-review, use `critique-task <run-dir>` for the actual screenshot paths/hashes and blank rubric from the canonical critique engine. Open all screenshots and inspect source/HTML and actual interaction evidence. Submit `critique-submit <run-dir> <review.json>`; verify using `critique-status <run-dir>`. Review records require specific observations and screenshot references for visual/interaction checks; each available capture needs a hash-bound observation. Core evidence, visual and engineering dimensions cannot be waived. Browser failures prevent declared design-review completion even if authored scores pass. The canonical rubric generates severity-ranked findings, unknown checks, repeated signatures and budget status; repair routes are advisory. `retry-artifact <run-dir> <new-run-dir>` preserves all replayed pre-build design stages and invalidates HTML binding, browser evidence and critique; use distinct output file paths, preserve original bytes, bind and capture again. For design changes use the earlier stage retry path instead. Artifact-only forks have a three-revision budget and inherited defect signatures. The review is authored, not automated aesthetic scoring, independent-reviewer authentication, or proof of functional/semantic parity. No delivery or release authorization yet. Browser CI pins Ubuntu 24.04 because Playwright 1.51.1 cannot install on Ubuntu 26.04; matrix jobs run independently.

## P4a: fail-closed local handoff and host boundary
Use `delivery-check <run-dir> <exact-file> [reviewed-candidate|unverified-draft]`. Reviewed candidates require replayed pre-build evidence, exact artifact bytes, complete observed browser pass, and replayed complete critique declaring an independent-human or independent-model reviewer with no findings. Reviewer identity is not authenticated. Explicitly agreed unverified drafts are permitted for verified browser blockers or browser-observed-pass with absent/pending critique, finding-free incomplete critique, or finding-free complete author self-review. Any recorded finding, browser failure, pending browser execution, unknown disposition, or stale/tampered evidence blocks the corresponding handoff. Draft verification is re-evaluated against current evidence; newly recorded defects invalidate earlier draft eligibility. Missing repository/CLI access permits only disclosed manual assistance outside the verified workflow, never an evidence-bearing handoff. `prepare-handoff <run-dir> <file> <new-dir> <mode>` writes an exact-byte HTML copy and manifest; `verify-handoff <run-dir> <handoff-dir>` recomputes eligibility, compares all manifest fields and the copied bytes. The draft label must accompany the draft when presented. Neither mode authorizes external transmission, release, or independent acceptance. Local JSON and hashes are not tamper-proof. A host-controlled sender must invoke verification independently immediately before sending the exact bytes, protect the verifier and evidence from model edits, and refuse direct sends that bypass it. The OpenClaw adapter contract is documented but NOT installed or tested in a real host. Do not claim host enforcement from local CLI tests.

## P0 semantic QA increment
After artifact binding use `semantic-task <run-dir>`, `semantic-submit <run-dir> <input.json>`, and `semantic-status <run-dir>`. See skills/infograph-master/references/business-semantic-qa.md. The deterministic engine evaluates authored observations against independent expected values/relations and explicit coverage dispositions; receipts bind source, HTML and revision and replay on delivery. Known failures block either mode; reviewed candidates require declared semantic checks pass. Missing/incomplete semantic evidence is labeled for otherwise eligible drafts. Optional per-case semanticProbes in the browser plan perform read-only DOM number, count and missing-marker checks after the declared interactions, using independently authored expected values. Failed probes fail the browser case; the verifier replays captured observation comparisons and requires probe coverage for passing cases. semantic-task exposes verified probe records; semantic-submit can hydrate observed values by report hash, viewport, case and probe ID, rejecting conflicting authored observations. This does not automatically discover business definitions, extract arbitrary source metrics, authenticate observations or provide comprehensive semantic coverage. Engine/package changes invalidate old runs; use a fresh run.

## P0 reviewer adapter increment
An optional operator-owned local subprocess adapter uses `reviewer-run --trusted-adapter <run-dir> <operator-config.json>` before critique submission. It receives the canonical task and exact evidence paths/hashes over stdin, returns a bounded JSON response over stdout, and is validated by the existing critique engine. Request/response receipts are replayed during critique and delivery; adapter failure never becomes a passing review. No shell invocation or built-in vendor network calls. Operator authorization and independence are declarations, not authenticated; executable is trusted, not sandboxed. See skills/infograph-master/references/independent-review-handoff.md for the contract. Real provider integration and host enforcement remain unverified.
