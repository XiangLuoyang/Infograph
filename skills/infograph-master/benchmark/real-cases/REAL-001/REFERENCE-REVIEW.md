# Reference-pair review workflow
Two distinct routes:
- Same-renderer regression: existing visual-baseline/visual-compare with strict capture compatibility.
- Concept-to-render: reference-pair-review, annotated corresponding objects/links, no pixel-equivalence assertion.

Prepare privately: reference image, candidate stage crop, image-bound annotations, manifest. Coordinates normalized to the reviewed region; use corresponding semantic state and matching region framing. Annotate visible ink vs container vs authored region explicitly; never treat a DOM bounding box as a silhouette. Record occlusion and ambiguous correspondences. Use original reference hash in image-sourced manifest. CLI verifies byte hashes (not image decoding or annotation authenticity); visually inspect sources and crops. Unknown evidence stays unverified. Default IoU/shift/area limits are authored engineering heuristics, not perceptual standards; predeclare alternatives and do not change after inspecting outcomes. Human reviewers assess actual appearance and motion; machine metrics are diagnostics only.
Run `node engine/reference-pair-cli.mjs manifest.json reference.json candidate.json reference.png candidate.png report.json [observations.json]`. Record scene-level human review of material, lighting, hierarchy and aesthetics; record interaction via actual running artifact. Every observation binds both image hashes. No automatic release authorization. Review repair scopes, change specific components, recapture, and preserve previous evidence. Do not upload private files to public CI.
The injected-defect browser fixture checks that an actual shifted DOM region is detected; link endpoint IDs are fixture metadata, not inferred from pixels. It does not measure real concept reconstruction quality.
