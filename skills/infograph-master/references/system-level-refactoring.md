# System-level dashboard refactoring (L3.1)

Trigger: existing dashboard with multiple pages/routes/tabs, repeated slices, shared state or substantial cross-section redesign; or explicit whole-dashboard optimization. Use this route before individual reconstruction. User-specified narrow scope stays narrow. The objective is complete assessment and coherent delivery, not mandatory changes to every slice.

## 1. Dashboard Atlas: enumerate before editing
Read navigation, routes, lazy/hidden views, source modules, rendered pages and reusable components. Inventory page and slice IDs independently of the redesign plan, with evidence locators and source revision. A slice is a meaningful information/interaction unit, not every DOM node. Reconcile navigation/source/render; record partial coverage when not all accessible. Map every inventory item to page/slice, including retained and out-of-scope items. Record purpose/task, parent page, shared data/filters/navigation/assets, and genuine execution dependencies (not every data relationship). No inferred unseen pages as facts.

## 2. Design DNA and global contract
For authorized standalone HTML load `references/design-dna-sampling.md` and use computed-style probes across representative pages/states/viewports. The sampler proposes observed role values and detects variants; the final comparison emits matched style observations for the ledger. Manual visual review remains required.
Sample representative original pages, slices, interaction states and actual rendered styles. Distinguish global patterns from exceptional one-off scenes. Record baseline and target for color semantics, typography hierarchy, material/depth, composition/density, chart language and interaction/motion. Define semantic role IDs and values, evidence refs, scope and approved exceptions. For exact CSS roles use canonical computed values with units; for chart/material/motion roles record an inspectable convention and verify via appropriate reviewer/renderer. Do not average incompatible styles. Do not mistake a list of colors for a design language.

Choose inherit (default for local modifications, no role change), evolve (targeted global evolution), or replace (new global language with migration of affected modules). Preserve approved identity. Every slice declares role usage; changed roles require migration across every dependent slice, not just newly designed ones. Specialized hero scenes may vary in representation while keeping typography/color semantics/interaction conventions; document exceptions and approval. Never add a new template that visually clashes with retained neighbors. If an intentional global change extends beyond user scope, do not apply without authorization.

## 3. Masterplan and coverage
Before editing create one decision for every discovered slice: retain / adapt / refine / restructure / reinvent / defer / out-of-scope. Each includes assessment evidence, actual reader-task impact, reason, priority, role usage and contract revision. Changed slices include concrete changes and semantic/functional preservation plan. Retain when effective; defer when not feasible and disclose remaining scope. Full scope includes every slice; targeted work still records outside scope. Do not call two edited slices whole-dashboard redesign unless every other slice was assessed and all planned work and checks completed.

## 4. Hierarchical execution and checkpoints
Use `references/system-batch-execution.md` for the executable batch loop, pre-build scoped DNA adapter and before/after contact-sheet review. Continue ready batches and preserve checkpoints; candidate failures do not advance the accepted artifact.
Work in layers: global architecture and shared style first; page responsibility and reading path next; then slice-specific reverse-design workflow; finally integration. Keep local plan.json and ledger.json (with source/plan/contract revisions). Start with a small representative batch; inspect it next to original and unaffected neighbors. Reuse shared components and style roles instead of local hard-coded overrides. For each batch select ready dependencies from the ledger, implement actual artifact, record output ref, update state and keep original. Do not mark a slice implemented just because planned. Do not overwrite other batches' changes; isolate edits, merge shared files serially. If context/budget ends, deliver current integrated artifact and explicit unfinished slices; resume from the ledger rather than restarting. On source, scope or contract change create a new revision and reassess impacted slices/checks. Multi-agent execution is optional and host-dependent, not provided by this tool.

## 5. Integration and global coherence
After batch implementation, review all pages and slices (including retained/out-of-scope neighbors) on final integrated output, shared state, navigation and data parity. Record actual output-bound evidence. Inspect contact sheets or matched page renders for hierarchy, visual rhythm, semantic colors, material, chart conventions, control behavior, responsive and accessibility defects. For each used style role compare observed value with contract target or approved exception. Observed mismatch is not resolved by declaring a new local style. Essential functions and metrics must remain; use existing reverse-design and runtime checks at slice and shared-state levels. No stylistic sameness requirement for legitimate content differences. Distinguish plan coverage, changed/retained/deferred, implementation completion and tested completion. Unknown and not-run remain incomplete.

## Tools and current boundary
Use engine/system-refactor.example.json as a synthetic structural example, not actual evidence. From skill root:
`node engine/system-refactor-cli.mjs plan plan.json`
`node engine/system-refactor-cli.mjs progress plan.json ledger.json`
The checker audits declared inventory mappings, dependency ordering, scope, style roles, migration, batch readiness and final-output-bound observations. It does not automatically discover all routes, extract computed CSS, render screenshots, write code or authenticate approval. Manually follow the same workflow if Node is unavailable; avoid dumping large intermediate JSON into user-facing output. A ready list is a planning aid, not parallel execution. Partial atlas, deferred slices, stale/missing final QA, mismatched roles and unfinished work prevent full completion. ScopeComplete for targeted work never implies fullDashboardComplete. Actual host adherence and real complex dashboard results remain untested.
