# VMI surface rendering V0.1 — bounded vector production

Use only after the selected concept passes existing semantic review. This is an optional actual SVG rendering route, not a replacement for VMI analogy search or rich concept-art/raster/3D specialist production.

## Structure
```sh
node scripts/infograph.mjs vmi-geometry
node scripts/infograph.mjs vmi-geometry rotor
```
Three normalized illustrative component templates (rotor, reservoir, valve) return actual existing primitive-compatible shapes, suggested decorative material assignments and optional moving-part/pivot hints. Inspect whether the physical object really matches the reviewed ontology/source anchor and target node; copy/adapt shapes into that object, keep the stable object ID and semantic bindings. Never substitute a visually similar but physically wrong device. The reservoir's static decorative fill and tick marks do not represent any data or calibrated level; remove them if they could imply measured capacity or add explicit qualitative annotation. A generic template is not an engineering drawing, real asset, physical simulation or universal geometry generator.

## Scene material and state contract
The existing VMI packet scene optionally carries:
```json
{"surfaceRendering":{"version":1,"rationale":"task-led material choice and scope","parts":[{"objectId":"b","shapeIndex":1,"material":"brushed-metal","encoding":"decorative-only","ref":"actual selected geometry evidence"}],"motions":[{"objectId":"s","shapeIndex":4,"kind":"rotation","encoding":"qualitative","pivot":[50,50],"angles":{"normal":0,"relief":-70},"ref":"verified qualitative transition evidence"}]}}
```
Material recipes: brushed-metal, matte-enamel, glass, rubber, liquid. Each targets an existing filled primitive, with unique object/shape identity. Gradients use the scene's current solid style tokens (ink, highlight, original fill role); the original stroke and geometry are preserved. Separate desktop/mobile gradient IDs avoid collisions inside the standalone preview. Use coherent light direction; avoid using decorative gradients on quantitative marks. Glass/liquid are opacity/tonal cues, not physical optical simulation. Keep essential labels live and on readable opaque surfaces.

Rotation is an explicit qualitative state pose, not a calibrated angle, load, speed, valve opening percentage or fluid simulation. All state angles are supplied and bounded; changes must agree with the reviewed concept transitions/changedObjects. Keep part geometry within its object in every pose; use actual browser and visual review to detect clipping/occlusion. The renderer applies the initial pose without JS, updates the actual SVG part on state change, interpolates CSS transform over the existing style motion duration and honors reduced motion. Existing static textual state comparison remains available. Do not invent a continuous motion mapping, add arbitrary physical connections, or imply a causal relationship absent from the verified semantic mappings.

Use the canonical vmi-packet route to compile and render the scene, compare variants, and inspect actual screenshots and state changes. The resulting HTML is a real standalone preview, not automatically embedded into the final dashboard. Integrating it into the production artifact requires preserving the scene CSS, identifiers, interactions, semantics, readable desktop/mobile composition and evidence; re-run actual artifact QA. Multiple scenes in one page require explicit SVG ID namespacing. Match the scene palette/font/material with the selected dashboard art direction through authored style tokens; no automatic conversion is claimed.

## Limitations
This first increment improves surface depth and reusable illustrative construction for existing SVG primitives. No realistic PBR, 3D mesh/lighting, generated images, generic physical topology, numeric liquid-level animation, real flow simulation, calibrated motion, automatic scene asset integration or independent aesthetics. Escalate complex physical geometry to the existing concept-art/reference pipeline rather than pretending a vector approximation is sufficient. Test fixtures are synthetic and must never be presented as real business evidence.

## Rich geometry production (P0.3 increment)
The `vmi-geometry` command now includes `tank`, `handwheel-valve`, `manifold-four` and `dial-indicator` in addition to legacy templates. On a scene object replace authored `shapes` with `geometry:{kind,anchor:{sourceId,nodeId},ref,reason}`. The selected anchor must exist in the reviewed concept and its corpus role must be compatible. For `manifold-four` add `branchCount:4,branchEvidence:"actual evidence reference"`; never use four ports for an unsupported number of branches. The compiler expands real primitives and decorative material bindings, preserves the semantic object ID and emits geometryManifest in the verified plan. A legacy hand-authored scene stays supported. Template selection is explicit and author-owned, not inferred automatically. Mixing authored shapes and template selection or duplicate generated/explicit material bindings blocks compilation. No automatic motion is added. Tank level, dial needle, branch width and valve pose are illustrative only, not encoded quantities. The browser checks selected geometry markers and primitive presence, not visual recognizability or physical correctness. Actual visual comparison and semantic review remain necessary. Connector ports, spatial topology and dynamic data binding are not implemented by this increment.

## Physical topology production (P0.3 increment 2)
After explicit rich geometry selection, optionally author `physicalTopology:{version:1,links:[{edgeId,kind:"pipe",fromPort:"out",toPort:"in",ref,reason}]}` on the scene. The edge must already be reviewed and bound; use only where a real fluid connection is the intended qualitative analogy. Available normalized ports: tank/out, handwheel-valve/in and /out, manifold-four/in and /out1..out4. The dial is deliberately not a flow-through component. Non-pipe relationships retain symbolic arrows. Ports are transformed using the nested SVG's actual xMidYMid meet geometry. The compiler rejects duplicate links, reused ports, incompatible directions, overlap of object/label boxes and routes that cross other objects or already-routed pipes. It tries bounded orthogonal candidates, or accepts explicitly authored `waypoints:{desktop:[[x,y],...],mobile:[[x,y],...]}` between port escape points; impossible routes block rather than fall back. Ordering may affect route feasibility. No automatic global placement, no generic pathfinding, no 3D, no physical simulation, no quantitative pipe width/flow, no collision guarantee for ordinary symbolic edges or actual rendered long labels. Direction arrows describe reviewed direction, not measured flow. Browser checks exact compiled visible route paths and endpoints. Reference/reason are authored evidence, not independent proof of physical equivalence. Review real geometry, flow semantics and readable labels separately.

## Responsive scene composition (P0.3 increment 3)
Opt in with `scene.composition:{version:1,mode:"auto",focalObject:"object-id",intent:"reader task",ref:"actual evidence",minSize:64,focalScale:1.3}` and omit desktop/mobile boxes on every scene object. For explicit selection use `mode:"select",candidateId:"row-grid2",reason:"why this candidate suits the task"` after inspecting `proposeSceneComposition` output. The compiler generates bounded row/grid/stagger/stack candidate pairs for 2–6 objects, using stable directed ordering with deterministic fallback for cycles. It reserves label strips and makes the declared focal object larger. Every candidate runs the actual physical topology compiler; blocked candidates record the error. The structural cost prioritizes symbolic object obstructions, strict line crossings, wire length and object scale. This is not aesthetic scoring, actual text measurement, or proof of comprehension. The selected candidate and comparisons are recorded as compositionManifest in the plan; the browser checks the selected ID and actual SVG box attributes. Manual coordinates remain supported; automatic mode cannot mix manual boxes or waypoints. The geometry/layout sizes are qualitative emphasis, not numeric encodings. Dense graphs, complex cycles, long labels, arbitrary routing, perspective and 3D remain specialist work.

### Non-linear graph composition
The candidate set now includes `layered` for directed acyclic graphs with branching layers (horizontal desktop, vertical mobile), and `hub` when the declared focal object is adjacent to every other object (radial arrangement). Cyclic graphs never use the layered candidate. Both new families reserve object and label boxes and are screened by the existing topology compiler and structural score; they are alternatives, not automatic aesthetic preference. A star may be better expressed as a focal hub, while a fork/join mechanism may suit layers. Do not interpret edge length, radial angle or node size quantitatively. This is still bounded 2D composition for 2–6 objects, not arbitrary graph layout or text measurement.

### Shared label-aware routing
Auto-composed scenes now compile symbolic paths against object boxes and estimated bottom-label rectangles using the actual target labels. Candidate scoring and rendering consume the same selected path data. The router tests direct, side/top anchored and bounded detour candidates; it penalizes shared collinear segments and records their total length in the structural metrics. It rejects candidates with no label-safe path and physical paths crossing estimated labels. Browser review checks exact selected symbolic paths and real SVG text bounding boxes against label, object and route overlaps. This is not typography measurement at compile time, a guarantee of zero crossings or arbitrary obstacle routing. Manual scenes retain the prior authored waypoint behavior. Label-aware audit applies to auto-composed scenes only. Review screenshots for arrowhead clearance, line distinguishability, legibility at scaled size, and aesthetic balance.
